# ADR 0016: Notebooks for the physicists who build on EICViBE

Status: accepted (2026-10-20; widgets and example notebooks 2026-10-21). Scope: `eicvibe.notebook` (its helpers, how a notebook shows EICViBE's objects, matplotlib plots drawn as the viewer draws, the viewer's own views as widgets), the `notebook` extra and the Jupyter kernel, the virtual accelerator client's ramp and tune monitor calls, and the views' data interface (`web/src/api/data.ts`, `web/src/notebook/`).

## Context

The viewer and the admin page are for the people who use the machine: they look at it, change settings, ramp it. Physicists also build on EICViBE: analyses of BPM data, corrections, matching studies, comparisons of the virtual machine with measured BPM files. That work is code next to its results, and Jupyter is where they write it.

The library already served notebooks: the virtual accelerator's client (ADR 0008), a run's history that another process reads while the run writes it (ADR 0007), `run_ring`, and an analysis that reads measured files and virtual runs alike. But each notebook repeated the same steps (read the machine and a mode's settings, choose an engine, start a ring with the machine's BPMs and ramp); an optics result shown in a cell printed every number of a dozen columns over thousands of occurrences; and nothing drew the machine's data the way the viewer does.

The viewer's pictures are React components drawing on a canvas, about 5,400 lines. They fetch their data from the server and read the page's state, so they cannot be called from a notebook as they are.

## Decisions

1. **Notebooks work on the library itself.** `import eicvibe.notebook as ev` gives one namespace: the library's engines, sessions, virtual runs, BPM data and analysis, and the client, with helpers for the steps every notebook repeats: `machine` (a machine folder), `mode_values` (an operating mode's settings), `optics` (a branch's, a line's from the fork that leads into it, a route's, in a mode, with either engine, as the viewer computes them), `session` (an engine's session, closed after its `with` block), `start_ring` (a virtual ring with the machine's BPMs, a mode's settings and the ring's ramp profile), `table` (pandas: a machine's branches, a result's values an occurrence a row, named), `viewer`. They return the library's own objects, so a notebook's code moves into a module or a tool unchanged.
2. **A notebook shows summaries, not every number.** Importing the module gives IPython, in HTML and in text, a few facts and a small table for a machine, an optics or orbit result, a tracking result, a ramp profile, a turn-by-turn acquisition, a slow orbit, a run's history and a running ring. The objects are unchanged: display is IPython's business, not the domain's. Results name branches by id; a branch whose lattice went through the module is shown by name.
3. **Plots are matplotlib, drawn as the viewer draws.** The element bar takes the viewer's colours, heights and lanes (`web/src/model/kinds.ts`): magnets above the axis when focusing and below when defocusing by the sign of their main strength, dipoles across it, instruments as ticks, forks as dashed flags. The optics keep the viewer's colours and the vertical dispersion its dashes. Beta and dispersion, and x and y, have panels of their own sharing s: two scales are never one axis's. Figures are made without pyplot, so they hold no global state; a notebook shows the figure a function returns, a script saves it. They are static: for scripts, papers and a quick look. Inside magnets where the engine sampled the optics (TrackPad).
4. **The kernel is EICViBE's environment.** The `notebook` extra (ipykernel, JupyterLab, anywidget, matplotlib, pandas) is in the dev group: `uv run jupyter lab` in the checkout. JupyterLab is in it because a widget's front end is found in the environment the Jupyter server runs in: one started beside the checkout (`uv run --with jupyterlab`) does not see the checkout's, and draws no widget. VS Code's notebooks take `.venv` directly. For a Jupyter of another environment, `uv run python -m ipykernel install --user --name eicvibe --display-name EICViBE` makes this one its kernel; that Jupyter needs anywidget too, for the widgets. **Engines run in worker processes of their own, as the server's do, never in the kernel** (`eicvibe.notebook.workers`: one per engine, started on first use, kept for the kernel's life): `optics`, `session` (a session open in the worker) and the widgets' optics go there, and virtual rings run in theirs, as always. Julia in the kernel hung it: TrackPad's optics computed in a JupyterLab kernel, the next cell waited for Python's GIL forever, with every Python thread of the kernel waiting for it too and Julia's threads idle (a task of Julia's left holding it; the kernel's channel and widget threads are what a script lacks, and runs with nbclient, without a front end, did not hang). With TrackPad in a worker the same notebook ran through, and the kernel stays free while an engine computes. A notebook's code run as a script needs `if __name__ == "__main__":`, since workers are spawned processes that import the script. Using an engine directly (`ev.engine("trackpad").open(...)`) still puts it in the kernel: Xsuite there is fine, TrackPad is not.
   An engine worker's process now ends with the process that started it (amending ADR 0006): a kernel restarted or killed with a ring running left the ring's worker waiting for calls that never came, holding its engine (Julia's runtime is a gigabyte) and the kernel's output; a server stopped by force did the same. The worker watches its parent and exits once it is gone, whatever signals it was left to ignore.
5. **The running viewer can be embedded as it is.** `viewer(branch=..., s=..., tab=...)` shows it in the notebook (an IFrame with a link's state): wholly interactive, sharing nothing with the kernel; runs a notebook writes appear in it when the server reads their folder (`--runs`).
6. **The client does what the admin page does to a ring's ramp**: `ramp`, `ramp_view` (the Ramp tab's data) and `tunes` (the tune monitor), besides settings, kicks, injections, captures and orbits.
7. **The viewer's own views are widgets the kernel feeds, each a view of its own** (2026-10-21). `ev.FloorView(machine, branch)` is the floor plan; `ev.OpticsView(machine, branch, result=..., values=..., mode=..., engine=..., s=...)` the optics under the lattice strip; `ev.OrbitView(machine, branch, runs=[...], s=...)` the runs' BPM orbits under the strip; `ev.chart({label: (x, y)}, ...)` the page's chart. Each draws with the page's own components in an [anywidget](https://anywidget.dev) widget (JupyterLab, Notebook 7, VS Code, Colab), with the page's interaction: hover and its readouts, selection, drag to zoom along s, forks followed, engine, fidelity and mode chosen in the optics view; and each stands alone (a first version had them in one widget, the floor plan always above the optics: the views are separate so that a notebook shows what it needs, where it needs it). Each is a module of its own, in Python (`eicvibe.notebook.widgets`: `floor`, `optics`, `orbit`, `chart`, on a shared base) and in the page's code (`web/src/notebook/`: `FloorWidget`, `OpticsWidget`, `OrbitWidget`, `ChartWidget`, on shared hooks for the lattice and what is shared); they are built into one ES module and stylesheet (`npm run build`; `vite.widget.config.ts`), which draws the view a widget names, so that React and the page's code come once. The page's stylesheet is scoped to the widget, and its dark scheme follows the notebook's theme (JupyterLab's or VS Code's, not the system's).
   - **Views are linked when asked to**, as the page's are: `ev.link(*views)` ties the branch shown, the selection and the s range (where both views have it), in the browser (`ipywidgets.jslink`), so the link holds while the kernel is busy; the views start from the first's values. Picking an element of another branch on the floor plan makes it the branch shown, which linked views along s follow. `ev.show(machine, branch, runs=...)` is no more than the floor plan, the optics and the orbits one under the other, linked.
   - **The views take their data through an interface** (`ViewerData`: engines, a branch's data, optics, a run's orbits and captures). The page gives them the server (`serverData`); a widget gives them its kernel (`kernelData`), asked over the widget's own channel and answered with the JSON the server would send, built by the server's code: `RevisionViews` for the lattice, `branch_optics` for optics, `RunCatalog` for a run's folder. Nothing else changed in the views; the floor plan, the strip and the chart were already given their data.
   - **The optics are computed by the engine's worker**, the one chosen in the widget, with the widget's mode and `values` (a matching's, say), and the widget is answered when they are (the kernel free meanwhile); each is kept for the widget, and `result=` shows optics already computed first, without computing them again. A ring is computed alone, a line with the branches its fork comes from (the worker's `machine_optics` takes `branches` now), a route along it.
   - **What a view shows is shared with Python**: `branch` (by name or id), `selection` (an occurrence's id, or a name in the branch shown; `selected` is the occurrence placed), `s_range` (`zoom(s0, s1)`) of a view along s, `engine`, `fidelity`, `mode` of the optics view, all observable. A selection from Python, or from a linked view, brings the element into view without zooming: Python zooms with `s_range`. Hover stays within a view.
   - A widget's orbits are asked for while the kernel is idle: a ring tracking in its worker goes on, and its orbits follow live; a cell running holds them until it ends.
8. **Example notebooks** (`notebooks/`, kept without outputs; `notebooks/README.md`): `01_rcs_ramp` ramps a virtual RCS and reads every turn of the ramp (tunes against energy, damping, charge, the bunch extracted); `02_orbit_correction` corrects a ring's orbit through the virtual accelerator in a sandbox (the BPMs through the client, the model built from the same machine files and the sandbox's live settings, a damped SVD written in the notebook beside `correct_orbit`, one logged change, the BPMs again); `03_bpm_data` writes a virtual run with hidden errors to an HDF5 file and measures tunes, phases and beta-beating from it, against the model and the truth. They read `EICVIBE_MACHINE`, `EICVIBE_RUNS`, and for the virtual accelerator `EICVIBE_URL`, `EICVIBE_TOKEN`, `EICVIBE_VA_MACHINE`. The client can now remove a sandbox (`remove`), so a notebook leaves none behind.

## Validation

- The EIN machine in a kernel: its summary; the RCS's optics with Xsuite (1 s) and TrackPad (9 s, Julia started in the kernel), the same tunes (28.2002, 27.4375); RTE's from the RCS's extraction fork; a virtual BAR ring started from the notebook; its spectrum; the RCS ramp profile. Every cell gave HTML or a PNG (executed with nbclient, rendered and looked at).
- A kicked virtual RCS run (2,048 turns, Xsuite): the BPMs' tunes 0.2004 and 0.4377 against the model's 28.2002 and 27.4375; the model's closed orbit and the BPMs' mean on one plot.
- `tests/notebook`: optics of a ring, of a line from its fork and of a route, in a mode; tables; summaries; IPython's formatters; the element bar's lanes and flags; the plots; a ring started with the machine's mode and ramp. `tests/va/test_ramp.py`: a ring ramped through the client, its ramp and tunes read back. `tests/engines/test_worker.py`: a worker's process ends within a moment of its parent's being killed (it stayed, without the watch).
- Three notebook runs with a ring left a worker each before the watch, which ignored SIGTERM and kept nbclient's output open; with it, none.
- The widgets in JupyterLab 4.6 (driven with Playwright, Chrome): the EIN's floor plan, strip and RCS optics (Q 28.2002, 27.4375); the optics' readout on hover; a drag zoom read back in Python (`s_range` 62.9 to 167.4 m); a quadrupole clicked in the strip read back (`selected.name` qfe2_2); Python's `zoom(100, 160)` and selection shown by the views, the zoom kept; the Orbit tab reading a kicked run's latest turns; the chart's readout; JupyterLab's dark theme followed. The page's own tests pass with the views' data through the interface (41 unit, 21 browser).
- The example notebooks, run with nbclient in fresh kernels: `01_rcs_ramp` in 66 s (TrackPad, 16 particles): the tunes held at 0.2005 and 0.4377 to about 7 GeV, the model's; near 9 GeV the kick's oscillation damped to the BPMs' noise (7 µm), and the strongest line in x became the synchrotron line (0.038); 15 of 16 particles extracted. `02_orbit_correction` in 129 s against a virtual accelerator (the RCS, its quadrupoles misaligned by 60 µm rms): 196 correctors a plane, rms 2.25 mm to 0.15 mm in x (predicted 0.10) and 0.91 to 0.08 mm in y (predicted 0.07); its correctors ramp in over the machine's 1024 turns, which the virtual RCS tracks at about 65 turns a second while 392 settings move, so the notebook waits for the run to pass the change's turn (the log's) and the ramp. `03_bpm_data` in 31 s: quadrupole gradients off by 0.3 % rms, BPM gains by 1 %: the file read back is the run's to 5e-10 mm; tunes measured 0.1999 and 0.4351, the truth's 0.1998 and 0.4350 rather than the design's 0.2002 and 0.4375; beta-beating 6.9 % and 6.3 % rms measured against 6.7 % and 6.3 % true, correlated at 0.96.
- In JupyterLab, `01_rcs_ramp` run cell by cell (Playwright): with TrackPad's optics in the kernel it hung at the next cell (above); with the engines in workers it ran through in a minute and a half, the injection's TrackPad optics shown by the widget (sampled inside the magnets), and the Orbit tab following the ring live while it ramped in its worker and the kernel was idle (turns 4,130 to 6,860 in 6 s). `03_bpm_data` ran through; its charts drawn.
- The separate views in JupyterLab, linked: a quadrupole clicked in the optics view's strip became the orbit view's and the floor plan's selection too (Python read `mqf21_2` from both views along s); a drag zoom in the optics view moved the orbit view to the same range (45.5 to 150 m); a BAR dipole picked on the floor plan moved the optics and orbit views to the BAR ring, the dipole selected there.
- `tests/notebook/test_widgets.py`: each view alone: the floor plan's branches are the server's JSON for the same lattice; the optics view's optics of a ring, a line from its fork, a route and a mode, errors as text; a result shown first is not computed again, the view's values count; Python moves a view by name; the orbit view's runs, orbits and captures; `link` ties what each pair of views has, from the first's values; the chart's colours. `web/src/notebook/kernel.test.ts`: requests and answers, asked once, a failure asked again, cancelled as fetch's are, failed when the widget closes. `tests/notebook/test_examples.py`: every example's code compiles; with `EICVIBE_RUN_NOTEBOOKS=1`, the two that need no server run from start to end.
