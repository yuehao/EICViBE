# ADR 0004: A shared web lattice viewer

Status: proposed (2026-10-07). Scope: floor geometry (`eicvibe.geometry`), the viewer API (`eicvibe.api`) and the web client (`web/`). Depends on ADR 0001; first step of REBUILD_PLAN §8 (machine explorer) and roadmap M3.

The first web screen shows one lattice revision three ways: a floor plan of every branch, a linear (synoptic) view of one branch along s, and its element table, with an inspector for the selected occurrence. Scientists use it to read optics settings and topology; engineers use it for positions, lengths, device and PV names, and CSV exports.

## Decisions

1. **The server keeps no per-user state.** Every endpoint reads an immutable revision addressed by its digest (`/api/v1/lattices/{digest}/...`). Branch, zoom, s range, selection and filters live in the browser and in the URL hash, so a link reproduces a view and nobody's browsing affects anyone else. This replaces the legacy `ViewerSession` shared by all clients (audit A01, A06, A09). There is no `POST /load`: the catalog is the set of lattice files and folders given when the server starts (audit A12).
2. **Responses are computed once per revision and served as bytes.** The catalog builds each response on first request (concurrent first requests wait for one build), keeps it with its gzip form, and revalidates with ETags. A changed file becomes a new revision; recent older revisions stay available, so a client is never switched under its feet. The client polls the listing and offers a newer revision, but never switches to it automatically. Several server processes (`--workers`) each hold their own cache, which is correct because nothing is shared.
3. **Per-occurrence data is columnar.** A branch is one response of parallel lists (table values and floor paths), which the client turns into typed arrays. For the RCS (2852 occurrences) that is 585 kB, or 95 kB gzipped.
4. **Floor geometry follows PALS and is computed by the package, not the client.** Bends use arc length, angle and `tilt_ref`, and patches use their offsets and rotations, so vertical bends and patches are placed correctly (the legacy web walk ignored both). Forks place branches in both directions: a fork places the branch it leads to, and a branch that forks into a placed branch is placed backward from it. A fork between two branches that are both already placed checks a loop and reports how well it closes (distance, angle). A fork that joins two traversals of one shared component at the same face matches the magnet's pole faces, not the reference orbits: a bend's entrance face is turned by −e1 from its orbit, its exit face by +e2, and other elements' faces are square to the orbit. This is how the EIN septum works: a rectangular magnet, a bend of −0.12 rad for the injected and extracted beams and a pulsed-off kicker for the stored beam, so the injected beam leaves it 1.75 mrad (e2) off the stored orbit. Matching orbits instead left the EIN loop open by 0.7 mm and 3.5 mrad (0.4 m × 1.75 mrad, twice); matching faces closes it exactly. Positions agree with MAD-X SURVEY to 1e-14 m.
5. **The client draws with Canvas 2D, not SVG.** This departs from REBUILD_PLAN §8, which keeps SVG until profiling shows a need. Here the floor plan shows every branch at once, which the legacy one never did, and the legacy SVG redraws its whole tree on every mouse move. Each branch becomes one `Path2D` per element kind in world coordinates. Pan and zoom change only the transform, hit testing uses a uniform grid, and hover and range updates bypass React. The table renders only its visible rows. The client was measured in headless Chrome at 1600×950 on the EIN (3.2k occurrences) and on a synthetic ring of 25k occurrences. Wheel zoom, drag pan, hover, linear-view zoom and table scrolling all held p95 frame intervals of 16.7 ms (60 fps); the largest single frame was 33 ms, in the 25k zoom. Controls, the table and the inspector remain HTML.
6. **Optics come from the engines, computed on the server like any other response.** `/api/v1/lattices/{digest}/branches/{branch}/optics?engine=…&fidelity=…` returns a branch's design optics: beta functions, alpha, dispersion and its slope, phase advance and the orbit, at the branch start and at every occurrence's exit, plus a ring's tunes, chromaticities and momentum compaction. A line's optics start from its own initial conditions or from the fork it starts from, and the response says which, or why a branch has none. The server computes the whole machine once per revision, engine and fidelity, in a worker process per engine (ADR 0006), and every client shares the result; concurrent requests wait for one computation without holding up other requests. TrackPad computes with TPSA maps (exact derivatives); its first request starts Julia (about 20 s), later ones take a fraction of a second. `/api/v1/engines` lists the engines installed. The linear view is a strip a third of its former height, directly above the optics plot in one panel; both use the same s range, scale and margins (wide enough for the plot's axes), so each element sits over its stretch of the optics. Dragging in either selects an s range to zoom to, right click undoes the last zoom, shift-drag pans. The plot draws beta on the left axis and dispersion on the right, with ticks and titles outside a framed plot area, and in field-free elements beta as its exact parabola rather than a straight line between exits. TrackPad also reports the optics inside magnets, at its integrator steps (10 per magnet at the standard fidelity, 40 at the precise one), which adds points and changes no result; in the BAR's combined-function bends the vertical beta peaks at 14 m between exits of 10.8 and 10 m, which straight lines between exits miss.
7. **BPM orbits come from virtual machines' runs, read like files.** `eicvibe-web --runs DIR` names folders of runs (ADR 0007, written by `eicvibe-virtual ring`, `eicvibe-virtual route` or a notebook); the server reads them as any reader does and starts nothing. `/api/v1/runs` lists them, each with its kind (ring or route) and what its turn numbers count (turns, or a route's shots); `/api/v1/runs/{run}/orbits?every=N&count=M[&end=T]` returns the BPM readings N turns (or shots) apart, the newest at the latest or at T - 1, with the events among them. Orbits of past turns never change and are kept; the page polls the latest once a second while the run goes on and its Orbit tab is shown. The Orbit tab draws x and y along s, the newest orbit bold with its BPMs marked and the older ones fading, and steps through what it shows when paused. For a ring it shows, as chosen (`source` of the orbits request; `/api/v1/runs/{run}/captures` lists the captures): the BPMs' buffer (the latest turns, live), the slow orbit (one sample per second of the run, live), or a capture (the buffer frozen by a kick, an injection, a beam loss or a request; ADR 0007). On a virtual accelerator's machine, Acquire captures the buffer now (a user logs in for it) and shows the capture once saved. Every user sees the same runs, as every user sees the same optics: a run is one virtual machine, and the server only reads it. What each user looks at (branch, range, tab, N and M) is the user's own. `--demo` runs the demo ring (Xsuite, paced at 2000 turns a second, kicked every 2048 turns) and four shots a second along the demo's `transfer` route, so the tab has something to show.
8. **A route is shown as a branch is.** A route is the beam's path through several branches, named by its branches in beam order in the machine folder's `routes.yaml` (ADR 0005), or in a `<stem>_routes.yaml` beside a lattice file. The summary lists each with its id `route:<name>`, its segments and length, and what keeps it from being one pass (a change of reference momentum at a join, such as the EIN's RCS to RTE, an acceleration). Wherever the API and the views take a branch id they take a route's: its optics are transported from the route's start through its segments (from the first branch's initial conditions, or the machine's optics where it starts part-way), each segment starting on its branch's design orbit; s is along the route. The top bar offers routes beside the branches. The client joins the branches' tables and floor paths into a route model once they have loaded, so the strip, optics, orbits and table draw it unchanged; the floor plan draws its path over the branches it passes, and the strip flags the forks along it. An element of a branch the route passes, found or selected anywhere, is selected on the route, which stays shown; the URL keeps the route (`branch=route:<name>`).
9. **One panel, three tabs, one strip.** Under the floor plan, the Optics and Orbit tabs share the panel and the lattice strip above their plots, with the same s range, zoom and undo. The Check tab checks a ring run's tracking against the model (ADR 0007): measured and model tunes, the spectra, tune and amplitude over the turns, phase advance, beta and orbit at every BPM, and on request the model's tune against amplitude; `check.html#run=<id>`, which the tab links to, shows the same on a page of its own, with room for its charts. The tabs stay mounted, so each keeps its choices (engine and fidelity, N and M) when another is shown; the URL keeps the tab (`tab=orbit`, `tab=check`).
10. **API types are generated.** `npm run generate-types` writes the OpenAPI document of the Pydantic response models and the TypeScript types from it. A Python test fails when the committed document is out of date.

## Layout

- `eicvibe.geometry`: `floor_geometry(lattice)` (frames of every occurrence, fork placement, closures) and `element_path` (sampled bend arcs). Depends only on the domain.
- `eicvibe.api.views.RevisionViews`: response models from a lattice and optional registry. No web framework imports; usable in notebooks.
- `eicvibe.api.catalog`: discovery (`<stem>_lattice.json` paired with `<stem>_registry.json` when it describes that lattice, and with `<stem>_routes.yaml`), revisions by digest, cached payloads.
- `eicvibe.api.runs`: the runs the server reads, and their orbits, kept once read.
- `eicvibe.api.app`: FastAPI routes and the static client; `eicvibe-web` (`python -m eicvibe.api`) runs it.
- `web/`: React and TypeScript client built with Vite into `src/eicvibe/api/static` (not committed; build it before packaging).

## Measurements

These were taken on 2026-10-07 on a development Mac, with one server process unless stated.

- EIN branch payloads: first request 21 ms, then 1.6 ms.
- 50 simulated users loading the whole view at once (1400 requests): about 2000 requests/s, p95 47 ms. 200 users: p95 190 ms with one process, 72 ms with `--workers 4`.

## Not yet

- Authentication. The server listens on loopback by default; the API is read-only and accepts no paths, but expose it only on a trusted network until OIDC (REBUILD_PLAN §12).
- Optics inside magnets with Xsuite: its plot joins the values at element exits. Xsuite's `twiss(at_s=...)` (deprecated for `cut_at_s` on a copy of the line) takes 7 s for the RCS at 0.1 m spacing; slicing its thick elements once per session would be the way.
- Optics with settings other than the design (a machine mode, the virtual accelerator's settings), and comparing two engines in one plot.
- Machine modes (the BAR mode settings), the registry's naming report, and live values from the virtual accelerator (ADR 0003).
