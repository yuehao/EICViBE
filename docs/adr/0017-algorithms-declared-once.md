# ADR 0017: Algorithms declared once, for the notebook, the virtual accelerator, the viewer and the AI's tools

Status: accepted in part (2026-10-24): step 1 is built, the three operations of ADR 0010 behind a catalog. Scope: how an algorithm written in a notebook (physics or AI) becomes one the virtual accelerator runs, the viewer offers and an agent calls; `eicvibe.operations.catalog`, the virtual accelerator's proposal request and `GET /va/operations`, and the viewer's Operate tab. Depends on ADR 0006 (engines), ADR 0008 (the virtual accelerator), ADR 0010 (operations as vetted tools, proposals) and ADR 0016 (notebooks).

## Context

Physicists write new algorithms in notebooks (ADR 0016): a correction, an analysis of BPM data, a tracking study such as `notebooks/Ex01_bar.ipynb` (a matched beam in the BAR, tracked with radiation, its damping times and equilibria). For others to use one, it has to run in the virtual accelerator, appear in the viewer, and be a tool an agent can call (ADR 0010, decision 3), without being written again for each.

The operations of ADR 0010 already had the right shape: a library function on a model of the machine as set, returning a `Proposal` that a person applies and the machine verifies. But each was written into every layer by hand: the function in `eicvibe.operations`; a branch of an `if`/`elif` in `VirtualAccelerator.propose`; its name in a `Literal` and its parameters as optional fields of one flat `ProposalRequest`, shared by all; and a form of its own in `OperateView.tsx`. The MCP tools would have been a fifth. Which measurement verifies an operation, and the shape of what it predicts, were tested by its name in the service and in the viewer.

## Decisions

1. **An algorithm is a library function with a typed contract, of one of three kinds.** An *operation* changes settings: `(MachineModel, parameters, measured) -> Proposal`, proposed, applied by a person (or an agent in its sandbox), verified (ADR 0010). An *analysis* reads data and writes nothing: `(BPM data and/or model, parameters) -> result`, such as the beta-beating of `notebooks/03_bpm_data.ipynb` or the run check of ADR 0007. A *study* is a long computation, run as a job with progress and a way to stop it, its data saved (HDF5, ADR 0007) and a result: Ex01's tracking, a scan, training a model. AI algorithms are of the same kinds: a policy or an optimiser that suggests settings is an operation, so the physics model checks its suggestion and a person approves it; a surrogate or an anomaly detector is an analysis; training is a study.
2. **Each is declared once.** A declaration gives its name, a label and a one-line summary; its parameters as a pydantic model, whose JSON Schema carries `x-form` hints (text before and after an input, the names of an enumeration's values, a placeholder, the other parameters' values it is shown for, or left out of the form as advanced); what it needs from the machine and how it is verified; the machines it runs on; and the function. The declarations import no engine, so the API is made from them when it starts.
3. **Everything that runs it is made from the declaration.** The virtual accelerator validates a request with the parameters' model and lists the declarations with their schemas; the viewer builds its form from the schema and draws a result by what it holds, not by the algorithm's name; the agent's tools (ADR 0010, decision 3) will be made from the same listing; a notebook calls the function. A new algorithm is added in its module and its declaration, nowhere else, unless it wants a view of its own.
4. **Code leaves the notebook when it follows the contract.** Its inputs are arguments, not the notebook's state: the machine as set comes from a `MachineModel` built from the virtual accelerator's settings, not from the design files (Ex01's BAR RF phase of π is the machine's setting, not the algorithm's). It chooses no engine: it uses the `Session` contract, so any engine, here or on an engine host (ADR 0015), runs it. Its result is typed, with units, and carries its own checks, as a proposal does; plots read the result. It is reproducible: a seed, and the lattice digest, engine and version, and for an AI model the digest of its weights, a file. It has a test with a known answer on the demo ring.

## Step 1, built (2026-10-24): the operations behind a catalog

- **`eicvibe.operations.catalog`** declares `orbit_correction`, `local_bump` and `tune_move`: each an `Operation` (name, label, summary, parameters, `verified_by` orbit or tunes, `machines`, and a function calling `correct_orbit`, `local_bump` or `move_tunes`). Each has its own parameters model (`OrbitCorrection`, `LocalBump`, `TuneMove`) with the fields, defaults and limits the shared request had, and the hints its form needs; a bump's place and amplitude are now required by the schema rather than by a check in the service. What the machine measured reaches an operation through `Measured` (the BPMs' latest slow orbit, read when asked for). The catalog imports only pydantic (a test checks that no engine is loaded with it).
- **The virtual accelerator** computes a proposal from the catalog: it finds the operation, validates the parameters, measures beforehand what will verify it (the slow orbit for an operation verified by the orbit, the tune monitor's reading for one verified by the tunes), and stores the request as validated (the operation's own parameters with their defaults, no longer every operation's). Verification chooses its measurement by `verified_by`, and an orbit's expected change by what the proposal predicts (`change` at the BPMs, or the orbit `before` and `after`). `Proposal.operation` is any declared name.
- **The API**: `POST /va/machines/{m}/proposals` takes the same flat body as before (the operation's name, its parameters, a reason), now one model per operation (`OrbitCorrectionRequest`, `LocalBumpRequest`, `TuneMoveRequest`) chosen by `operation`, made from the catalog; `GET /va/operations` lists the operations with their parameters' JSON Schemas. An unknown operation or a missing parameter is refused with 422, as before.
- **The viewer's Operate tab** reads `GET /va/operations` and builds its form from the schemas: a select for an enumeration, a number or text input otherwise, the hints for labels and units, the fields shown only when their `when` holds (MICADO's count), the advanced ones left out (damping, the channel lists), the button kept off until the required fields are filled. Values are kept by parameter across operations. A prediction is drawn by what it holds (tunes, an orbit before and after, or a change), and the menu offers only the operations for the machine's kind.

Validation: the operations' and virtual accelerator's tests pass unchanged (`tests/operations`, `tests/va`, an agent's orbit correction, a bump and a tune move each proposed, applied and verified against the BPMs or the tune monitor), with new tests of the catalog and the listing; the web client's types are regenerated from the API; the Operate tab's browser test proposes a bump through the generated form, applies it and verifies it against the BPMs.

## Order of work

1. The operations behind a catalog (built).
2. An analysis: the beta-beating of `03_bpm_data` on a run's capture, listed, its form generated, its result drawn as a table and a chart along the ring.
3. A study, with the job machinery: Ex01's tracking of a matched beam with radiation (its damping times from the one-turn map, its moments every N turns saved as HDF5, the equilibria), started from the viewer, its progress shown, stopped on request.
4. The MCP server's tools made from the listing (ADR 0010, step 3).
