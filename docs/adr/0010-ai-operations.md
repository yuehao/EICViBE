# ADR 0010: Accelerator operations as vetted tools, which a model may choose and a person approves

Status: accepted in part (2026-10-11): the tools and skills come first, served over MCP to existing harnesses (decision 3), and EICViBE's own agent after them; an agent applies to its own sandbox freely, and a person approves anything applied to a shared machine (decision 2); the first operations are orbit correction, local bumps and tune knobs, chromaticity after them. Scope: a new `eicvibe.operations` (the physics of bumps, orbit correction, tune and chromaticity knobs), proposals in the virtual accelerator (ADR 0008), the tools that expose both, the procedures a model reads (skills), and the agent that uses them. It changes ADR 0009 decision 5 ("it reads; it never acts") for these tasks only, and does what its "Not yet" asked first: orbit correction and the other operations as tools in their own right, before any agent.

The request (2026-10-11): the AI should use the accelerator knowledge that exists, so that a local bump, an orbit correction, or a tune correction or move is done the way accelerator physicists do it, with the most reasonable knob and without disturbing other properties; skills, MCP or a harness should make sure of that, learning from DeepSeek Harness and opencode.

## What others found

- **A model is a poor optimiser and a good coordinator.** On ARES (DESY), the best of 14 language models tuning five magnets reached −50 % of the objective where Bayesian optimisation reached −93 % and a trained policy −99 % ([Kaiser et al., Sci. Adv. 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC11691695/)); the authors expect models to coordinate such algorithms instead.
- **Facilities that use agents give them vetted tools.** Osprey (ALS, at seven DOE facilities) has the model plan, find control channels against a validated list, and configure existing tools (Xopt/Badger optimisations at LCLS); every write is approved by an operator against per-channel limits and step sizes; since 2026 it runs on Claude Code as its harness with MCP tool servers and skills per workflow ([arXiv:2508.15066](https://arxiv.org/abs/2508.15066), [IPAC'26 MOP6322](https://indico.jacow.org/event/95/contributions/12485/)). GAIA (DESY) is a ReAct agent with a local model calling the control framework as tools ([arXiv:2405.01359](https://arxiv.org/abs/2405.01359)). A DOE workshop (Jan 2026) agreed on a co-pilot: read-only by default, writes gated by a person, planning separate from execution, plans validated on a digital twin first, shared MCP tools and reusable skills ([SRN](https://doi.org/10.1080/08940886.2026.2649097)). No published agent does bumps, orbit correction or tune moves through physics tools on a ring.
- **Harnesses make tool use dependable.** DeepSeek Harness ([deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)) runs every tool call through one pipeline: logged, checked before (permissions, sandbox, a person's approval), checked after (a hook may block or replace the result), logged; "model-visible means logged". opencode ([opencode.ai](https://opencode.ai/docs/permissions/)) sets each tool to allow, ask or deny, has plan and build agents, and loads skills. Skills (SKILL.md, [agentskills.io](https://agentskills.io/)) are procedures a model reads when a task needs them, with scripts for what must be exact; MCP is the interface tools are called through. Both work with local models (Ollama) in these harnesses. Neither checks that a result is right: that is the tools' job.

## Decisions

1. **The physics is EICViBE's, in code, never the model's.** `eicvibe.operations` computes each operation by the method accelerator physicists use, from the model of the machine as it is set (the virtual accelerator's settings, not the design), with any engine:
   - **Response matrices** by finite differences through an engine session (`Session.update`, `orbit`, `optics`), later from TPSA maps (ADR 0006): orbit (BPMs × correctors, each plane, and the dispersion column), tunes, chromaticities, beta-beating and dispersion against knob families.
   - **A closed local bump**: three correctors around the point (amplitudes from beta and phase, θ₂/θ₁ = −√(β₁/β₂)·sin(φ₃−φ₁)/sin(φ₃−φ₂), θ₃/θ₁ = √(β₁/β₃)·sin(φ₂−φ₁)/sin(φ₃−φ₂)), or four for position and angle at a point; the correctors chosen so that the phases between them are well short of π and the strengths within their supplies' limits; closed in the model, with the orbit outside the bump unchanged.
   - **Orbit correction**: least squares on the response matrix by SVD, with singular values cut or damped (Tikhonov), BPM weights, corrector limits; MICADO when few correctors should move (one error to find); the RF frequency (or energy) column in rings; dispersion-free steering on transfer lines.
   - **Tune moves and corrections**: a knob from quadrupole families (in the EIN's rings, the strings), whose matrix stacks the tune rows with weighted beta-beating and dispersion rows, so that the tunes move with the least beating; the chromaticity's change reported.
   - **Chromaticity**: two sextupole families.
   Each gives a **proposal**: the setting changes (channels, in device units through the transfer functions), what they should do (the orbit at every BPM, tunes, chromaticities, the largest beta-beat, dispersion), the checks made in the model with the changes applied (a bump's leak outside it, the tune reached, the headroom of every supply), the method, and its references. The operations work without any model: from a notebook, the command line and the viewer.
2. **A proposal is applied by a person, or to a sandbox.** The virtual accelerator keeps proposals: made, previewed, applied (atomically, through the write path with its reason and correlation id, ramped per turn), verified (what the BPMs and tunes then show against what the proposal predicted) or discarded, each an action in the log. Applying to a shared machine needs a person with the physicist role to approve it in the viewer, whatever made the proposal; an agent may apply to its own sandbox. A tune monitor is needed to verify tune moves: the virtual rings' `btun` channels get values (from the turn-by-turn BPM data, as a tune monitor's).
3. **One set of tools, for any harness.** The operations and the machine's state are tools with typed arguments and results: reading (settings and limits, orbits, tunes, optics, devices by name, the log), computing (propose a bump, a correction, a tune move; nothing is written) and acting (apply a proposal to a sandbox, ask a person to apply one to a shared machine, verify one). They are served two ways: an MCP server (`eicvibe-mcp`, over the virtual accelerator's API with the user's own account), so that Claude Code, opencode, DeepSeek Harness or Osprey can use them with their own approvals; and to EICViBE's own agent (decision 5). Results are high-signal (numbers with units, the checks, what to do if something fails), and errors say how to fix the call.
4. **Procedures are skills.** Each task has a SKILL.md: when it applies, which tool and which knobs, the parameters to choose, what must hold before and after (a bump's leak at the BPM noise, the tunes reached within 0.001, the orbit's rms falling as predicted), what not to do (a bump across a septum, a tune knob through the injection region), and references. A machine's own skills say which knobs it has (the EIN: its correctors, its rings' quadrupole and sextupole strings, the RCS's ramp). They are plain files, in the agent-skills layout, so any harness that reads skills can use them, local models included.
5. **EICViBE's own agent is small and strict.** In the viewer, a request in words ("a 1 mm horizontal bump at rcs_bpm_12", "correct the BAR's orbit", "raise Qx by 0.01 without moving Qy") runs one loop: read the skill, call the tools, show the proposal with its predictions and checks, wait for a person, apply, verify, report what the BPMs and tunes show. The tools are set to allow (read, compute) or ask (apply); a step limit and a guard against repeated calls stop it; everything the model sees and does is logged (ADR 0008). It uses the configured model (ADR 0009: local by default; a model that calls tools). The model chooses the operation and its parameters and explains the result; it never states a strength or a prediction the tools did not give.
6. **A benchmark comes before the agent is offered on shared machines.** Tasks with known answers on the virtual accelerator (bumps of given size and place, orbits with known errors to correct, tune moves) measure how often the agent chooses the right operation and parameters and reaches the target without side effects; agents and models are compared on it. Until it passes, the agent works in sandboxes only.

## Order of work

1. `eicvibe.operations`: response matrices; orbit correction; bumps; tune knobs; tests on the demo ring and the EIN against the formulas and the model.
2. Proposals in the virtual accelerator, with preview, approval, apply and verify; the tune monitors; a viewer panel to make, preview and approve proposals by hand.
3. The tools, the MCP server and the skills, used from opencode or DeepSeek Harness with a local model, and from Claude Code.
4. EICViBE's agent in the viewer and the benchmark; chromaticity.

## Step 1, built (2026-10-11): `eicvibe.operations`

`MachineModel` is one engine session of a branch as it is set (`MachineSettings.start_values` of the live channels), with its BPMs (registry devices), correctors (channels setting `Kn0L` or `Ks0L`) and quadrupole channels (strings and single supplies setting `Kn1`); the operations change channels, in their units and limits, and get the lattice values through `MachineSettings`, so a string moves every magnet it drives. Each returns a `Proposal` (pydantic: the changes, the predictions, the checks, the method, references), written to nothing.

- `correct_orbit(model, plane, orbit=None, method="svd"|"micado")`: the response matrix by finite differences of the closed orbit (a ring) or the trajectory (a line), kept for the machine as set except its correctors; SVD with Tikhonov damping (1 % of the largest singular value), raised until every corrector is within its limits; MICADO with an exchange pass (greedy choice alone missed the pair that explained two errors on the demo ring: 0.907 mm left instead of 0.001). Predictions are the full model's, not the matrix's; correcting the model's own orbit, it corrects again what one step left, and recomputes the matrix once where the orbit (through the sextupoles) changed it; a check warns when the full model departs from the matrix by more than 10 %: apply, measure and correct again.
- `local_bump(model, plane, at, amplitude, angle=None)`: three correctors, or four for position and angle, solved on the model's response for the offset (and angle) at the point and zero orbit and angle after the last corrector; of the three nearest correctors on each side, the set that uses the least of their range; checked in the model: amplitude, angle, and the orbit change at every BPM outside (its leak).
- `move_tunes(model, dqx, dqy, quadrupoles=None)`: the tune response met exactly with the least beta-beating (Δβ/β at every element, both planes) and dispersion change (1 cm weighing like 1 %), by constrained least squares over the quadrupole channels (two: the 2×2 response inverted); Newton steps in the full model; checks: tunes within 1e-4, beta-beating within 5 %, dispersion change within 5 % of the ring's largest, limits; the chromaticity's change reported.

Results (Xsuite, standard fidelity):

| machine | orbit correction (rms, mm) | bump | tune move (+0.01, +0.01) |
| --- | --- | --- | --- |
| demo ring | x 1.279 → 0.015 (SVD), → 0.001 (MICADO, 2 correctors) | 1 mm, 3 correctors; 0.5 mm and 0.1 mrad, 4; leak < 10 nm | (+0.01, −0.005), 22 channels: beta-beating 1.9 %, two channels alone more than twice that |
| BAR | x 1.041 → 0.012, y 0.519 → 0.001 | 2 mm, leak 0 | 4 strings: beta-beating 6.2 %, fails the 5 % check (too few knobs) |
| RCS | x 11.4 → 0.078 (matrix recomputed once, 63 s), y 1.69 → 0.023 | 2 mm, leak 0 | 12 channels: beta-beating 0.24 %, dispersion 0.68 mm |
| LTR (line) | x 0.952 → 0.008 | 1 mm, leak 0 | a line has no tunes |

An RCS response matrix (196 correctors, 192 BPMs) takes 22 s a plane and is kept. Tests: `tests/operations` (errors made with correctors, found and undone; bumps closed; tune moves exact, with the least beating).

## Step 2, built (2026-10-11): proposals in the virtual accelerator

- **Agents' tokens.** `agent` tokens (made in the viewer's account menu) carry their user's rights in the user's sandboxes; on a shared machine they propose and verify only, and cannot apply, write, act as operators or administrators, or make tokens (ADR 0008, decision 10).
- **Proposals** are computed on the machine as set (its mode and live values) and as its BPMs last read (the slow orbit), with the model tracked as the ring is: 6D with its RF. That mattered: a horizontal three-corrector bump closed in the 4D model leaked 0.25 mm all round the 6D ring, since a kick in a dispersive region lengthens the path, and with the RF holding the frequency the energy changes and the orbit with it. A horizontal bump in a ring with RF now takes one more corrector, so that the energy (the path length, Σθη) stays as it was, as control rooms keep bumps energy-neutral; vertical bumps keep three.
- **Apply and verify.** A proposal is applied atomically through the write path if the machine is still as it was proposed for (else it is stale); verification waits for the ramp and a measurement after it, then compares the orbit change at the BPMs (the predicted change against the measured one, within 5 % of its size plus 5 µm: the BPMs' 1 % gain errors and noise) or the tune monitor's change (within 5e-4 or 10 %).
- **The tune monitor** reads the beam's own motion, as a BBQ (ADR 0007).
- **The viewer's Operate tab** proposes (log in on the first one), shows each proposal (its checks, changes, the predicted orbit at the BPMs, the method and references), applies it (asking again if a check failed), verifies and discards it, and lists those an agent made.

Tests, on the demo's virtual accelerator: an agent proposes an orbit correction on a shared machine whose two correctors were set wrong and cannot apply it; a physicist applies it; the BPMs then show the change predicted. A stale bump is refused; a vertical bump and a tune move (+0.01, +0.005) are verified by the BPMs and the tune monitor; an agent applies in its own sandbox and is refused administration. In Chrome: a physicist proposes a horizontal 1 mm bump in the Operate tab (four correctors, the energy kept), applies it and verifies it against the BPMs.

## Not yet

- Bayesian optimisation (Xopt/Badger-like) as a tool, for tasks without a model-based method (injection efficiency).
- Bumps held by orbit feedback (NSLS-II folds them into its slow feedback as targets); corrections per time slice of the RCS's ramp.
- Calibrating the model from measured response (LOCO) before computing corrections.
- The RF frequency as an orbit-correction knob (the energy column), and operations on a route's lines in the virtual accelerator.
- Hidden magnet errors in the virtual rings (ADR 0008), so that an orbit correction has more than the BPMs' offsets to find.
